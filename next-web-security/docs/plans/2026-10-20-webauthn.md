# Web Authentication: the plan

Date: 2026-10-20
Status: Phases 0-5 are done — 113 tests in `webauthn/` and `web/webauthn/`.

## Where it stands

`HttpSecurity::web_authn` installs the four endpoints of the two ceremonies, the
provider that turns a verified assertion into a login, and the registration page
it always contributed. A relying party identifier and a `UserDetailsService` are
required, and both are reported when the chain is built rather than when a login
fails.

Phase 0 was not actually done when this plan was written down as "waiting on the
encodings": `ciborium`, `coset` and `p256` were absent from `Cargo.toml` and from
the lock file. They are dependencies now, and the two encodings they unblocked
are decoded in `webauthn/cose.rs` and `webauthn/attestation.rs`.

Everything else the ceremony needed was already built when Phase 4 started: the
options of both ceremonies, the client data and its checks, the header of the
authenticator data, the attested credential of a registration, the challenge
store, and the credential store.

Phase 5 is done as well: `WebAuthnRegistrationFilter` serves
`/webauthn/register/options` and `/webauthn/register` for the user the request is
authenticated as, `WebAuthnAuthenticationFilter` serves
`/webauthn/authenticate/options` and `/webauthn/authenticate`, and
`WebAuthnAuthenticationProvider` turns a verified assertion into a login with the
authorities of the user the credential belongs to.


## What a ceremony needs

A passkey login is three checks piled on each other, and the port had none of
them:

1. **CBOR.** The attestation object and the authenticator data extensions are
   encoded with CBOR. `ciborium` provides it, and `coset` builds the COSE key on
   top of it.
2. **COSE.** The public key of a credential travels as a COSE key: an elliptic
   curve point or an RSA modulus, tagged by algorithm. `coset` decodes it;
   `webauthn/cose.rs` reads the algorithm, the curve and the coordinates out of
   it.
3. **The signature schemes.** ES256 and RS256 over
   `authenticatorData || SHA-256(clientDataJSON)`, verified with `p256` and the
   `rsa` crate the port already depended on.

All three are dependencies and code now. EdDSA, P-384 and P-521 are refused by
name rather than accepted untested: ES256 and RS256 are the two algorithms the
specification makes every authenticator support.

## Phases

### Phase 0 — the dependencies

Done: `ciborium 0.2.2`, `coset 0.4.2`, `p256 0.14.0` are dependencies of the
crate, and `cargo test -p next-web-security` builds them. The registry has to be
reachable once; after that the lock file pins them.

### Phase 1 — the types of the ceremony

`PublicKeyCredentialCreationOptions`, `PublicKeyCredentialRequestOptions`,
`RelyingParty`, `PublicKeyCredentialUserEntity`, `PublicKeyCredentialDescriptor`,
`Credential`, and the two responses. This is data plus serde, and it is the part
that can be written and tested without any cryptography.

### Phase 2 — the parsers

- `clientDataJSON`: base64url, then JSON — `type`, `challenge`, `origin`,
  `crossOrigin`.
- `authenticatorData`: `rpIdHash` (32 bytes), flags, sign count, then the attested
  credential data and the extensions, both of which are CBOR.
- The attestation object: `fmt`, `attStmt`, `authData`.

Each of these is a pure function from bytes to a struct, which makes it the first
place a test can be written: fixtures in, structs out.

### Phase 3 — the credential store

A trait with an in-memory default, like the SAML replay cache:
`save(credential)`, `find_by_credential_id(id)`, `update_sign_count(id, count)`.
The relying party of a WebAuthn deployment is a user, so the credential carries
the user name.

### Phase 4 — the ceremonies

Done, in `webauthn/manager.rs`, and every check it makes has a test — including
the ones the plan's table below lists as the negative cases.

Registration: fresh challenge, remembered for one submission with a TTL; verify
that `clientData.type` is `webauthn.create`, that the challenge is the stored one,
that the origin is the expected one, that `rpIdHash` is the hash of the relying
party id, and that the flags say the user was present. Then store the public key.

Authentication: the same checks with `webauthn.get`, then verify the signature and
require the sign count to have grown when the credential reports one — a
regression is the clone signal.

The attestation statement itself: accept `none`, and reject the rest explicitly
rather than silently. Spring's default conveyance is `none`, so this is the
honest first scope; `packed` and `tpm` are a later phase.

### Phase 5 — the filters and the configuration

Done, matching the Java names: `/webauthn/register/options`,
`/webauthn/register`, `/webauthn/authenticate/options` and
`/webauthn/authenticate`. Two decisions were made rather than copied:

- The challenge is not kept in the session. It is stored by the relying party and
  consumed once, keyed by the ceremony it was issued for, so the second half of a
  ceremony does not depend on a cookie surviving the first half.
- A registration runs for the user the request is authenticated as, and the
  request never names a user. An endpoint that took the user from the body would
  let anybody register a passkey for anybody.

The browser side of the same phase — the passkey form of the login page, the
registration page, and the script that calls the four endpoints — is
`plans/2026-10-21-webauthn-browser-half.md`.

## The test vectors

The same rule as the SAML side, for the same reason: **a vector produced by the
code under test proves only self-consistency.** The fixtures have to come from
another implementation — the FIDO alliance conformance tools, or a browser's
authenticator — and be committed as data.

The negative cases matter more than the positive one, and each of them is a test
— `docs/verification-matrix.md` names the test of each row:

| Case | Expected |
|---|---|
| origin of another site | refused |
| `rpIdHash` of another relying party | refused |
| replayed challenge | refused |
| challenge never issued | refused |
| challenge of the other ceremony | refused |
| expired challenge | refused |
| tampered signature | refused |
| sign count going backwards | refused |
| `USER_PRESENT` flag clear | refused |
| user verification required and not done | refused |
| credential id of another user | refused |

The signatures the ceremony tests sign are made with a key the test holds, which
proves the plumbing and not the arithmetic. The arithmetic is anchored by the two
signature vectors of RFC 7515 — appendix A.2 for RS256 and A.3 for ES256 — which
another implementation produced: they are the only signatures here that this port
did not make.

## Effort

Phase 1 and 2 are a session each. Phase 3 and 4 are one session. Phase 5 is half
of one. Phase 0 turned out to be one command once the registry was reachable.

## What not to do

Do not hand-roll CBOR to avoid the dependency. It is a simpler format than XML
canonicalisation, but it is parsed from attacker-controlled bytes and it is the
decoder of every attestation, which puts it in the same class as the signature
work: worth a crate, not worth a weekend.
